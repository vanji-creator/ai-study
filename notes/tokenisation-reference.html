1 · What tokenisation is

A model cannot read text. Its first layer is a lookup table with a fixed number of rows, decided before training and never changed afterwards. So every input must arrive as row numbers: a list of integers.

Tokenisation is the process of cutting text into pieces that exist in a fixed dictionary, and replacing each piece with its ID. A piece is called a token, and a token is usually part of a word, not a word. The tokeniser is that dictionary plus the ordered rules used to build it.

Two words that get confused Tokenisation is the process. Tokeniser is the thing that performs it: the dictionary plus the merge list.

2 · Two pipelines, not one

A tokeniser is built once and used forever. Those are two separate pipelines that run at different times, and almost every confusion about tokenisers comes from mixing them.

 Pipeline A — buildPipeline B — use
WhenOnce, offline, before the model is trainedOn every single request, forever
InputA large corpus of textOne piece of text
OutputAn ordered merge list + a vocabularyA list of integers
MathsCounting. No neural network.Table lookup. No neural network.
Changes later?Never. Training the model does not touch it.Deterministic — same text, same IDs

3 · Pipeline A — build the tokeniser

A1

Corpus

What happens
A large pile of plain text is collected. Nothing is trained here. The text is only counted.
What it decides
The language mix decides which languages get cheap tokens. The domain mix decides whether code, URLs and maths tokenise well. The size decides how reliable the counts are.
Afterwards
The corpus is discarded. Only the merge list survives.
The consequence that lasts forever A mostly-English corpus means English pairs win every count and English pieces get the rows. Every other script then pays more tokens for the same meaning, for the whole life of that model. It cannot be fixed later.
A2

Pre-tokenise and count

What happens
The corpus is cut into chunks, usually at spaces and punctuation, and each distinct chunk is counted. The space stays attached to the front of the chunk that follows it.
Why chunks first
It stops merges from ever crossing a word boundary. Without it, a frequent pair like e_t spanning "the cat" would become a token, and tokens would straddle words.
Real number
Counting CLAUDE.md this way gives 1,355 distinct chunks.
A3

Split into bytes

What happens
Each chunk is encoded to UTF-8 and becomes a sequence of single bytes, each a number from 0 to 255. This is the starting state: every piece is one byte long.
Why bytes and not letters
Letters would need about 150,000 rows to cover every script. Bytes need 256 and cover everything that can exist in a file.
A4

Count pairs, merge the most frequent, repeat

What happens
Every pair of neighbouring pieces is counted across the whole corpus, weighted by how often its chunk appears. The most frequent pair is joined into one new piece everywhere, and recorded. Then the counting starts again on the new state.
Stopping
It stops after a fixed number of merges, chosen in advance. That number is the vocabulary size. It does not stop when counts get small.
What emerges
Frequent whole words become single pieces. Frequent word parts — ing, est, er — become pieces because they recur across many words. Nobody defines a suffix; counting finds them.
A5

Output: the merge list and the vocabulary

Merge list
The merges in the order they were made. Order matters: replaying them out of order gives different tokens.
Vocabulary
A dictionary from piece to integer ID: 256 byte rows, then one row per merge, then the special tokens.
Real number
Our run: 256 + 400 merges = 656 rows, plus 2 special tokens.

4 · The frozen tokeniser

The vocabulary has three kinds of rows, and one of them lives in a channel that user text cannot reach. That separation is the reason chat boundaries work at all.

5 · Pipeline B — use the tokeniser

B1

Raw text

What happens
A string arrives — a user message, a retrieved document, a system instruction. At this point it is characters, and the model cannot use any of it.
B2

Normalise

What happens
Optional clean-up before splitting: Unicode normalisation so two ways of writing the same character agree, and sometimes lower-casing.
Watch out
Modern tokenisers usually keep case, because case carries meaning. Whether a given tokeniser normalises at all is a property of that tokeniser — check, do not assume. Our own script lower-cases, which is a simplification.
B3

Pre-tokenise

What happens
The string is cut into chunks by the same rule used in A2, so runtime matches training. The space attaches to the word that follows it: 'the café is' becomes ['the', ' café', ' is'].
Why it matters
This is what makes _the and the two different tokens, and it is the whole reason a trailing space damages output.
B4

Encode to bytes

What happens
Each chunk becomes UTF-8 bytes. ASCII characters take 1 byte; other scripts take 2, 3 or 4. ' café' becomes [32, 99, 97, 102, 195, 169] — six bytes for five characters, because é needs two.
Why nothing is lost
UTF-8 is reversible. é is never replaced by e; the pair 195, 169 means é and only é.
B5

Apply the merge list, in order

What happens
Merge 1 is applied everywhere it fits, then merge 2, and so on to the end of the list. No counting happens here — the counting was done once, in A4.
Unseen words
They are not a special case. replaying was never in the corpus and still becomes r | e | play | ing, because those merges exist. Anything with no merges stays as single bytes.
B6

Pieces to IDs

What happens
Each piece is looked up in the vocabulary and replaced by its integer. This is a dictionary lookup and cannot fail, because every single byte has a row.
What the ID means
Nothing yet. It is a row number, like a primary key. Meaning is learned later, during model training, from seeing that row in many sentences.
B7

Add special tokens

Who does it
Your application, or the provider's server — never the model, and never the user. The boundary IDs are placed around the content, not derived from it.
Result
One flat list of integers. The model sees only this. It has no idea a template existed.

6 · Decode — the way back

The model produces IDs, one at a time. Turning them back into text is the same table read in reverse.

Why a streaming answer can pause mid-word A multi-byte character can be split across two tokens. The bytes of a half-finished character cannot be decoded yet, so the text appears only once the following token arrives.

8 · One merge step, drawn

Corpus: low×5, lower×2, newest×6, widest×3. Every pair of neighbours is counted, weighted by how often its word appears.

9 · Why other languages cost more

Two separate causes, both pushing the same way. Stating only one of them is a half answer.

CauseMechanismEffect
1. More bytes per characterUTF-8 gives ASCII 1 byte; Tamil, Japanese and similar scripts take 3 bytes per characterThe sequence starts about 3× longer before any merging
2. Fewer merges applyThe counting corpus is mostly English, so English pairs win the counts and get the rowsOther scripts stay close to the byte level and are never collapsed

Together these give the 3–5× token ratio between a sentence and its English translation. Both are decided in Pipeline A, before the model exists.

10 · Special tokens

Rows that correspond to no text: end of text, start and end of turn, padding, and a mask marker for models trained to fill in blanks. They are ordinary rows to the model, which learns what they mean from training, exactly as it learns _the.

What makes them special is that the tokeniser will not produce them from user text. Typing the marker characters yields ordinary piece rows with different IDs. Structure therefore travels in a channel content cannot write into.

Who inserts them — two shapes

 Way A — string firstWay B — IDs first
MethodBuild one string containing marker text plus message text, then tokenise it with special-token parsing enabledTokenise each message separately with special tokens disabled, then join the ID lists with special IDs
Common?Yes — most chat templatesLess common, safer
RiskUser content sits inside a string that is being parsed for markers. It must be stripped or escaped first.User content is never parsed for markers
First security control of the course User-supplied text is always tokenised with special tokens disabled. The application adds boundary IDs itself. With a hosted chat API this is enforced at the API boundary, because you send roles and content, not tokens. When you run a model yourself, the choice is yours. Returns in Block 9.

11 · The trailing space

Measured on CLAUDE.md: the first merge learned was a space joined to a letter, and 132 of the first 250 merges produced a piece beginning with a space. _the earned a row; bare the did not.

A:  "The capital of France is"       ->  … _is            next token: _Paris   common
B:  "The capital of France is "      ->  … _is  _         next token: Paris    rare

In B the space has already been spent, so _Paris would produce two spaces and is unavailable. The model must use a bare piece instead. Two rare things now coincide: a lone space token, which almost never appears in training because spaces merge into the next word, and a space-less word piece. The model is in a state it seldom saw, and the output degrades — odd spacing, a weaker answer, a stray newline.

Rule: never end a prompt with a trailing space or an unintended newline. It matters most in completion-style calls and in few-shot examples you build by hand; in a chat API the template appends boundary tokens after your content, so your text is not last.

15 · Self-quiz, cold

Answer out loud before opening each one. Tick the ones you missed; the count is kept in this browser.

Why can a byte-level tokeniser never fail on an input?
Every input is already bytes, and all 256 possible byte values have rows. There is always a fallback piece, so no text in any script can produce a missing entry.
What decides which pieces become tokens?
Frequency in the counting corpus. The most frequent pair of neighbouring pieces is merged, and that repeats a fixed number of times.
When does the merging loop stop?
After a fixed number of merges chosen in advance — the vocabulary size. Not when counts get small.
Does training the model change the tokeniser?
No. The tokeniser is built before training and is frozen. Model training changes the embedding rows, never the merge list.
The same sentence gives 22 tokens on one model and 30 on another. Why?
Different merge lists, learned from different corpora, with different vocabulary sizes. The tokeniser is a property of the model.
Give both reasons a Tamil or Japanese sentence costs more tokens than its English translation.
(1) UTF-8 uses about 3 bytes per character instead of 1, so the sequence starts longer. (2) The counting corpus was mostly English, so few merges apply and the text stays near byte level.
What does the integer ID of a token mean?
Nothing on its own. It is a row number, like a primary key. Meaning is learned during model training from seeing that row in many sentences.
Why is a word-level vocabulary a bad idea, in two ways?
Unseen words have no row at all and collapse into one junk entry. And the long tail is huge — 64.5% of distinct words in CLAUDE.md appear once, so most rows would barely be trained. It also separates shared roots like play and playing.
Why not use single letters for everything?
It never fails, but sequences become roughly 4× longer, and attention cost grows faster than linearly with length. The model must also rebuild every word from letters before using it.
Is é ever replaced by e?
No. e is code point 101 and é is 233, two different characters. é is stored as the two bytes 195 and 169, which decode back to é exactly. Nothing is approximated.
Why does UTF-8 use two bytes for é when 233 fits in one byte?
Byte values 0–127 are reserved for ASCII characters. Any byte above 127 signals that more bytes follow, so 233 alone would be ambiguous.
What is the output of tokeniser training, and what happens to the corpus?
An ordered merge list plus a vocabulary mapping pieces to IDs. The corpus is discarded.
How is a word the tokeniser has never seen handled?
Not as a special case. The merges are replayed in order; whatever matches is joined, and the rest stays as smaller pieces or single bytes. replaying → r | e | play | ing.
Why must pre-tokenisation happen before merging?
To stop merges from crossing word boundaries. Without it, a frequent pair spanning two words would become a single token.
Which token does a space belong to, and what follows from that?
The word after it. _the and the are different tokens, and a trailing space in a prompt leaves a rare lone-space token that forces the model into an unusual state.
What makes a special token special?
It is a row that no user text can produce. Typing the marker characters gives ordinary pieces with different IDs, so message boundaries live in a channel content cannot write into.
Who inserts special tokens, and when can a user forge one?
The application or the provider's server, before the model runs. A user can forge one only if the application tokenises user text with special-token parsing enabled and does not strip the markers first.
How does generation stop?
The model produces the end-of-turn ID itself. The serving code sees it, ends the loop, and does not display it.
Why can you not use tiktoken to estimate Claude costs?
It is OpenAI's merge list. It undercounts Claude by roughly 15–20% on ordinary English and more on code and non-English text. Use the provider's own counting endpoint.
Two tokenisers, one built on English news, one on Python source. Which gives fewer tokens for def calculate_total(items):?
The one built on Python source. Its corpus contained def, (, ): and identifier patterns often enough for them to earn rows. The news tokeniser splits the punctuation and identifier into many small pieces.

16 · What I got wrong on the first attempt

Revision list — re-check these cold in week 11 1. Believed the dictionary entry itself carries meaning. It does not — the ID is a primary key, and meaning is learned during model training.

2. Believed the merge loop stops when counts drop. It stops after a fixed number of merges, decided in advance.

3. Believed pieces let the tokeniser accept a small spelling mistake as the right word. It never corrects or approximates — birdz becomes bird | z and stays birdz.

4. Could give only one of the two reasons non-English text costs more. The missing one was the merge list being learned from a mostly-English corpus.
